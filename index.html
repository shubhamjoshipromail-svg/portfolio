The thing I noticed

I keep building a checkpoint between an AI and a consequence.

I didn't plan this. It only became obvious looking back at six unrelated projects.

In AgentDock, an agent can't send an email without a human approving it — and no configuration exists that turns that off. In RxCheck, the model may explain a drug interaction but never assert one; the pharmacist always sees the underlying source. In OpsPilot, low-confidence tickets route to a person instead of being silently misrouted. In the CMS work, every number had to survive a hostile reading by someone with an opposing interest, because it feeds a policy argument other people will attack.

Four industries. Same instinct: work out where the machine should stop and a person should decide.

It's the direction I'm most curious about now, and I think it gets more urgent rather than less. As AI stops producing text and starts taking actions in the world, the gap between "the model was confident" and "someone is accountable" becomes the expensive part.

I'm not claiming that's a company yet. It's the pattern I'd want to attack with a co-founder.

Agent infrastructureTypeScript · Next.js · PrismaActive

AgentDock

A governance control plane for multi-agent AI. Every tool a flow touches passes a deterministic policy gate before anything executes.

The shape of it

Two modes. Build — describe an outcome, generate or load a flow, inspect its agents, tools, memory, approvals and budget, then run a metadata-only preview. Control — a board of real runs, each separating its Output (the deliverable) from its Process (a collapsible step log), plus an approval inbox and spend tracking. Control shows real runs only; no demo data.

The parts that were actually hard

Durable execution. Runs enqueue to a Postgres job queue and execute on a standalone worker with lease and heartbeat. Kill the worker mid-run and the job is reclaimed on lease expiry and resumes from the last completed agent via a step cursor. SELECT … FOR UPDATE SKIP LOCKED, with a per-user concurrency bound.

Idempotent external actions. A retried step never double-fires a real-world effect. This is the line between a demo and something you'd point at a live mailbox.

Real MCP execution. Built on the official SDK, speaking the actual wire protocol — initialize → tools/list → tools/call — so adding a capability is "connect a server, grant it, gate it" rather than hand-writing an executor per tool.

The policy gate. Deny-by-default. Permissions clamp server-side and never loosen, ordered read_only < draft_only < approval_required < blocked. Unverified external servers force approval; restricted-risk tools are blocked outright.

The Gmail boundary. create_draft writes a real draft and asks first, because it's still a mailbox write. send_email is classified as an external write and is always approval-gated — there is no configuration under which a send auto-allows. An instruction buried in untrusted content still stops at approval.

Flow truth. Saving is fully reconciling, not add-only. Remove a tool from a flow and both its row and its access grant are deleted in the same transaction, so a revoked permission can never linger and be honored at runtime. What you build is what runs.

Real today

  • Google identity; user-scoped agents, flows, grants, runs, approvals in Postgres
  • Model-backed flow planning with Zod validation and server-side clamping
  • Real governed runs on encrypted BYO provider keys
  • Durable queue, crash recovery, step-cursor resume, SSE event streaming
  • Idempotent external actions across retries
  • MCP revocation with kill-switch semantics
  • Integration tests against a separate Postgres test database

Not real yet

  • Sandbox isolation — boundary defined at the callMcpTool seam, not implemented
  • Third-party MCP servers — only the allowlisted first-party one connects
  • Billing, payments, org spend reconciliation
  • Embeddings and semantic memory retrieval
  • External agent runtimes, cross-org agent identity
  • No users outside me. No revenue. No design partner.

Clinical decision supportPython · FastAPI · ReactLive

RxCheck

A pharmacist-facing drug interaction checker. The interesting engineering isn't the AI — it's the boundary drawn around what the AI is allowed to say.

A two-table interaction model keeps a canonical pair row plus per-source assertions, with lexicographic ordering enforced by a CHECK constraint so (A,B) and (B,A) can't both exist. Normalization runs RxNorm exact match → brand lookup → trigram fuzzy → NDC fallback, and confirmed fuzzy matches are written back as aliases so a repeat typo resolves instantly.

The LLM layer is RAG-only: structured interaction rows go in as context, every response is schema-validated, and a cross-check confirms the model referenced only drugs present in the source data. Failed validations are logged and never shown. Hub-drug scoring surfaces which single medication change would most reduce interaction burden for a polypharmacy patient — a question pure severity ranking can't answer.

Designed against FDA Non-Device CDS criteria so a pharmacist can always see the basis of an alert. Frozen run snapshots mean the audit trail reflects what the pharmacist actually saw, not what the data says now. All of it exists because alert fatigue is the failure mode that actually matters.

Policy dataClient engagementOngoing

Alliance of Community Health Plans

ACHP represents nonprofit and community-based health plans and advocates for them in national Medicare and Medicaid policy debate. Analysis like this is built to be used in that advocacy, by an organisation whose opponents have every incentive to attack the numbers. That made accuracy and defensible interpretation the whole job — not the modelling.

The question: when CMS cut Medicare Advantage reimbursement for 2026, how did ACHP members and national carriers differ in how they shifted costs onto beneficiaries?

I built a four-step ingestion pipeline across CMS Landscape, ACHP Crosswalk, monthly CPSC enrollment and Plan Benefit Package data, producing dual-year master files of 138,000+ plans across 208 columns. Along the way I found and corrected a 12x enrollment overcount, reconciled schema drift between years, and matched 109,015 plan-county rows. Kaiser was isolated separately because under 6% of ACHP plan-county rows represented roughly half of ACHP enrollment.

Findings: 67.5% of national plans eroded drug benefits versus 41.3% of ACHP plans, with weighted deductible increases of $114 against $26. ACHP held a cost advantage in 493 of 875 scored counties. The analysis supports a clear ask — that CMS be required to show year-over-year changes in deductibles and out-of-pocket exposure alongside premiums, rather than premiums alone.

01 · CLOSEST TO WHAT I'M BUILDING

The accountability layer for agents that act

Permissions for AI agents currently live in a prompt, the audit trail is a log file, and the spend cap is a person remembering to check. Databases got roles, cloud got IAM, Kubernetes got admission controllers — capability ships first and the control plane arrives second. AgentDock is my attempt at that second thing.

What would have to be true: someone is already maintaining a homegrown version of this and hates it. If every team I meet says they'd rather accept the risk than add a gate, the idea is wrong and I should drop it.

Strongest counterargument: this collapses into the agent frameworks and model providers and never becomes a standalone layer.

02 · WHERE I THINK IT GOES

The same problem, once AI touches physical things

Every checkpoint I've built sits between a model and a reversible consequence — an email, a routing decision, a recommendation on screen. As AI moves into systems that act on the physical world, the same question sharpens and the undo button disappears. "The model was confident" and "a person is accountable" are not the same sentence, and the gap between them stops being an abstraction.

What would have to be true: people building embodied systems are hitting this now, not in five years, and solving it with something worse than what could exist.

What I don't know: whether this is a real near-term problem or a thing I find intellectually attractive. I'd want to meet people in robotics before spending a year on it.

03 · FROM THE HEALTHCARE WORK

Making regulated-industry data defensible by default

The CMS engagement took months mostly because government data is a mess — schema drift between years, a 12x enrollment overcount sitting in the source, no reconciliation path between filings. Every claim had to survive a hostile reading. That work is repeated, badly, by every organization touching this data, and almost none of them find the overcount.

What would have to be true: enough organizations do this repeatedly that a shared reconciliation layer beats everyone rebuilding it.

Why I'm cautious: it might be consulting with extra steps rather than a product.
